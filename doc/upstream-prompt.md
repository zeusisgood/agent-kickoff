# 原本への提案プロンプト（雛形）

案件で生まれたルールを原本（agent-kickoff）に入れるための指示文です（rules 13 章）。

- 原本に PR を出せる環境では、エージェントは作業の前に「原本を直すときの注意」を読む。
- 出せない環境では、下の「プロンプト」の `<…>` を埋めて 1 本にまとめ、ユーザーに渡す。ユーザーはそれを、PR を出せる環境のエージェントに貼る。

## 原本を直すときの注意

- agent-kickoff は**案件のテンプレート**でもある。次のファイルは案件向けの雛形なので、このリポ自体の指示として読まない。内容も変えない（雛形そのものを直す提案の場合を除く）。
  - `AGENTS.md`・`CLAUDE.md`・`CHANGELOG.md`
  - `doc/spec/`・`doc/adr/`・`doc/architecture.md`・`doc/TODO.md`
- 従うのは `doc/rules.md` の本文（ブランチ・コミット・PR の決まり）。
- 直すのは次の 3 つ。
  - `doc/rules.md`：本文と、冒頭のルール版（`YYYY.M.N`）。
  - `doc/rules-adr/`：新しい ADR。番号は原本の最新の次を振る。一覧の `README.md` にも足す。
  - `doc/rules-changelog.md`：一番上に新しい版の節を足す。
- 原本ではタグも GitHub Release も作らない。版は `doc/rules.md` 冒頭のルール版と `doc/rules-changelog.md` の節で表す（rules 3 章の「タグ」は案件向け。`release.yml` は案件の `CHANGELOG.md` を読む）。
- 雛形のファイル（`.claude/`・`.devcontainer/`・`KICKOFF.md`・`README.md` など）も変える必要があれば、変更履歴にそのファイル名を書く。
- ブランチは `<エージェント名>/<内容が分かる英語>`。PR は出すが Merge はしない。
