# 0001. 決定を ADR に残す

- 状態：承認
- 日付：2026-10-21
- 関連：rules 1 章・7 章

## 背景

コードからは「何をしているか」は分かっても、「なぜそうしたか」「なぜ他の案を採らなかったか」は分からない。理由が残っていないと、Claude は過去に却下した案を何度も提案してくる。

今の置き場所では足りない。

- コードコメント：その箇所の判断しか書けない。
- コミット本文：履歴に埋もれて探しにくい。
- 仕様書：版ごとの文書なので、ずっと有効な決定が古い仕様書に埋もれる。

## 決定

版をまたいで有効な技術・構成の決定を、1 決定 1 本の ADR に残す。

- 連番で `NNNN-<英語の題名>.md` とする。
- 中身は 背景・決定・採らなかった案・結果・未決事項。
- 状態は「提案 → 承認 → 置き換え」。
- 案件の決定は `doc/adr/`、共通ルールの決定は `doc/rules-adr/` に置き、番号は別々に振る。

## 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 仕様書に「採らなかった案」の欄を足すだけ | 決定が日付ごとの仕様書に散らばり、今も有効かどうかが分からない |
| 参考記事どおり、作成スキル・Slack 通知・定例まで入れる | 複数人のチーム向けで、一人開発には過剰。スキルは作らない方針（[0002](0002-public-template-repo-no-skill.md)） |
| 日付のファイル名（仕様書と揃える） | 「0004 を 0012 で置き換え」のように参照しにくい |
| テーマごとにまとめる | 一部だけ変えたいとき、置き換えの単位が大きすぎる |
| ルールの ADR を `doc/adr/` に置き、案件では消す | 案件の Claude Code がルールの理由を読めなくなる |
| ADR にせず、rules.md に理由を 1〜2 行ずつ書く | 採らなかった案を十分に書けず、rules.md が長くなる |

## 結果

- 良くなること：今も有効な決定が一覧で分かる。却下済みの案を蒸し返されにくくなる。
- 引き受けること：書く手間が増える。書く基準（後から変えると手戻りが大きいもの。迷ったら書かない）を守る必要がある。
