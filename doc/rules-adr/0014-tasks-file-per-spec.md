# 0014. 作業の分解を、仕様書とは別の TASKS ファイルに書く

- 状態：承認
- 日付：2026-10-21
- 関連：rules 2 章

## 背景

仕様書には「何を作るか」はあるが、「どの順番で作るか」と「どこまで進んだか」がない。長い実装の途中で止まったときや、セッションをまたぐときに、どこから再開するかが分からない。

先行事例の GitHub Spec Kit と Kiro は、どちらも仕様から作業の一覧（tasks）を作り、進み具合を更新している。

## 決定

- 仕様書を承認したら、実装の前に `doc/spec/TASKS_YYYY-MM-DD_<内容>.md` を書く。仕様書と同じ日付・内容名にして、1 対 1 で対応させる。
- 中身は、実装の順番のチェックリスト（1 項目は 1 コミット程度）と、再開のためのメモ。
- 終えた項目に印を付け、同じブランチでコミットする。
- 書くのは実装するエージェント。チャットでは作らない。

## 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 仕様書の中に節として書く | 進み具合を更新するたびに仕様書の差分が増え、承認した内容との区別がつきにくい |
| 作業の分解を書かない | 中断からの再開に弱い |
| Spec Kit のように、機能ごとのフォルダに spec・plan・tasks などを分ける | 文書が多くなりすぎる。仕様書と tasks の 2 つで足りる |
| GitHub Issues に分ける | 通信と権限が要る。エージェントが手元で読み書きしにくい |

## 結果

- 良くなること：中断やセッションのまたぎから再開しやすい。進み具合が PR の差分で分かる。
- 引き受けること：ファイルが 1 つ増える。チェックの付け忘れがある。
